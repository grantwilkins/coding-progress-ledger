\section{Experimental Setup}
\label{sec:setup}

The setup to test our program is a synthetic, architecture-grounded migration
instance for a \emph{single provider serving one model family}. A source site runs
the provider's Qwen3 suite (Table~\ref{tab:models}): the hybrid-linear efficiency
tier Qwen3-Next-80B, the small and dense mid tiers, and the Qwen3-235B flagship.
The KV size $\eta_q$ is exact from each model's published attention config
($\eta = \text{layers}\times\text{KV-heads}\times d \times 2_{(K,V)}\times 2$\,B at
BF16), spanning $24$\,KiB/tok for Next-80B (only its full-attention layers hold
per-token KV) to $256$\,KiB/tok for the dense 32B, which is KV-heavier per token
than even the 235B flagship. The prefill rate $\rho_q$ is log-interpolated from
per-tier anchors at $\{1,10,100,1000\}$k tokens, and context bytes are
$\beta_q=4$\,B/tok (uint32 token ids).

We specify the workload by \emph{token share}, not job count, and the provider is
flagship-primary: the 235B handles $55\%$ of served tokens. Each tier's context
length is sampled from a per-model log-normal fit~\cite{servegen} (medians
$5$k--$15$k tokens, clipped to $[10^3,10^6]$), and job counts are \emph{derived} as
$n_m \propto s_m/\bar T_m$ from the token share $s_m$ and clipped mean length
$\bar T_m$. Because the flagship serves the longest agentic sessions, it is a token
majority but a job minority (${\sim}24\%$ of sessions). The flagship's token share
is our primary mix-sensitivity knob. We group sessions into classes by model and
log-token bucket, which decouples the solve cost from $N$ exactly, since every load
is linear in $T_q$.

Three destination sites differ in both network and GPU capacity, with ingress
$\Lambda_\ell\in\{12.5,25,50\}$\,GB/s and GPU pools $W_{\ell m}$ of one to three
instances per model. The GPU pools are partitioned per model, so an instance
for one model cannot serve another. The pools are sized in HBM: each
instance is one TP=8 group ($8{\times}$H100 $=640$\,GB), holding the model's
resident BF16 weights ($60$--$470$\,GB) plus KV headroom, and the flagship is the
dominant HBM line item per site. State ingest runs at $\mu=512$\,GB/s per
instance (8 GPUs $\times\,64$\,GB/s PCIe Gen5, host-staged), so the network, not
ingest, is the binding transfer resource by construction. The deadline $D$ is the
control we sweep, and a stranded job is charged $d^{\mathrm{miss}}=2D$, the next
recovery window. Table~\ref{tab:setup} collects the parameters. These are controlled
scenario values chosen to exercise the resource tradeoffs, not measurements of a
specific production cluster.
