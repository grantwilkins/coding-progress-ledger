## Wall-clock data (N6 follow-up)

The 20 run dirs under `runs/swe_agent_live/` were generated with the default replay-time clock; per-event intervals are microsecond-scale and V1's wall-clock columns populate with values too small to be physically informative.

A parallel batch under `runs/swe_agent_live_wallclock/` covers the same 20 instances with **synthetic-clock** timestamps (`--synthetic-clock-start 2026-05-01T00:00:00+00:00 --synthetic-step-seconds 30`). Every run in that batch has `timestamp_span_seconds >= 60`, and `seconds_since_progress_increase` exceeds 1.0 on 664/704 step rows. `live_instrumentation.json::timestamp_source` distinguishes the two batches (`replay` vs `synthetic`). Neither batch is true wall-clock data from a freshly-running SWE-agent process; that path remains available via the sidecar's stdin streaming and was not exercised here because the upstream nebius/SWE-bench traces lack per-step timestamps.

## Notes on the live-vs-retro progress gap

The systematic pattern — live progress at or near 1.000 even when retrospective is lower — is the **expected, documented** consequence of the N4 frontier policy:

> Raw-step live instrumentation does not invent discovered-but-unattempted validation obligations. Submit-without-validation is represented as `complete_visible_frontier+no_validation_frontier` unless the agent emits explicit `ledger_ops` for validation work.

Every divergence above is consistent with that policy: the retrospective annotator added a VALIDATION leaf for bug-fix tasks that the agent did not exercise (per the validation-implicit-for-bug-fix guideline), while the raw-step live channel cannot infer the missing leaf without explicit `ledger_ops`. See `runs/swe_agent_live/PARITY_REPORT.md` and `runs/swe_agent_live/EVENT_OBSERVABILITY_MATRIX.md` for the full treatment.

This decoupling between progress shape and outcome is also a feature, not a bug — see the project memory note "Progress signal decoupled from outcome by design".
