# Observation distribution comparison: toy/live runs vs SWE-agent pilot (F4)

This document satisfies `TASKS.md` § Workstream F, task **F4**. It
reports distributional differences between the two populations of
ledgers in the framework: the **toy/control/live** runs at
`datasets/ledger_observations_v0_step.csv` (18 runs, the framework's
original evaluation corpus) and the **SWE-agent pilot** runs at
`datasets/swe_agent_pilot_observations_step.csv` (20 runs, the new
real-trace pilot). Per § F4 acceptance, the report says whether
SWE-agent traces are more diverse than toy/live runs and flags any
toy/live property that does not survive on real traces.

## 1. Headline comparison

| Metric                                       | Toy/control/live (N=18) | SWE-agent pilot (N=20) |
|----------------------------------------------|-------------------------|------------------------|
| Runs                                         | 18                      | 20                     |
| Step rows (total)                            | 198                     | 191                    |
| Rows per run (median / min / max)            | 9.5 / 4 / 26            | 10 / 5 / 15            |
| Final coding-progress (median / min / max)   | **1.00 / 0.60 / 1.00**  | **0.90 / 0.50 / 1.00** |
| Final overall-progress (median / min / max)  | 1.00 / 0.60 / 1.00      | 0.92 / 0.50 / 1.00     |
| Non-monotonic runs (any negative δ)          | 14 / 18 (78%)           | **20 / 20 (100%)**     |
| Total reopens / splits / invalidations       | 6 / 8 / 3               | 3 / 0 / 0              |
| Active-coding denominator at end (median)    | 4.5 (max 9)             | 4.0 (max 7)            |
| Distinct drop-sources observed               | 3 (validation, product, mixed) | **4 (product, validation, investigation, mixed)** |
| High-progress failures (upstream label)      | 0                       | **1 (`f_06`)**         |
| Low-progress successes (upstream label)      | 0                       | **1 (`s_04`)**         |
| Success/progress quadrants populated         | 2 of 4                  | **all 4 of 4**         |

## 2. The most load-bearing finding

**Toy/live data populates only 2 of 4 success/progress quadrants.**

```
                           progress < 1.0    progress = 1.0
              ┌─────────────────────────────┬─────────────────────────────┐
   success    │ 0 toy runs                  │ 15 toy runs                 │
              │ 1 SWE-agent (s_04)          │ 9 SWE-agent (s_01-03,05-10) │
              ├─────────────────────────────┼─────────────────────────────┤
   failure    │ 3 toy runs (neg_control_*)  │ 0 toy runs                  │
              │ 9 SWE-agent (f_01..f_05,    │ 1 SWE-agent (f_06)          │
              │   f_07..f_10)               │                             │
              └─────────────────────────────┴─────────────────────────────┘
```

The toy corpus has nothing in the **success-low-progress** or
**failure-high-progress** quadrants. The SWE-agent pilot populates
both, and they are exactly the shapes that distinguish a process
observation channel from an outcome classifier:

- **`f_06`** (failure at progress 1.00): all discovered work
  completed; failure sits in undiscovered hidden work — the agent's
  repro never actually triggered the bug. The toy/live corpus has
  no equivalent because every toy task was authored by us; we
  always knew what the work was.
- **`s_04`** (success at progress 0.67): submit-without-validation
  succeeding by luck. The toy/live corpus has no equivalent
  because the toy harness mechanically ran tests for every run.

A modeler training on the toy/live distribution alone would never
see these shapes and could not learn that `progress=1.00` does not
imply success, or that `success=True` does not imply
`progress=1.00`. The pilot adds the off-diagonal data that makes
the framework's "progress is decoupled from outcome" claim
empirically defensible.

## 3. Property-by-property survival on real traces

### 3.1 Non-monotonicity is universal on real traces

Toy/live: 14 / 18 runs (78%) show at least one negative coding-progress
delta. SWE-agent: 20 / 20 (100%). Every real trace exhibits the
"add-leaf-before-completing-it" pattern that produces a saw-tooth
progress curve. The toy/live corpus has 4 monotonic runs because
some toy runs were authored to be linear.

**Implication:** any modeling assumption that "progress monotonically
approaches 1.0" is wrong on real traces.

### 3.2 Drop sources are richer on real traces

Toy/live drop_source counts: `validation: 12`, `product: 8`,
`mixed: 1`. SWE-agent: `product: 17`, `validation: 24`,
`investigation: 14`, `mixed: 1`.

The toy corpus has no `investigation`-sourced drops. SWE-agent
shows 14 of them, generated by stuck-loop traces (`f_03`, `f_07`,
`f_02`, `f_10`) where the investigation leaf is added but never
completes — its presence in the active denominator drops progress
without any per-step coding-progress recovery.

**Implication:** a model that classifies failure modes from
drop-source alone will lose the entire investigation-blocked
category if trained on toy/live only.

### 3.3 BLOCKED status is essentially absent in toy/live

Toy/live has no `BLOCKED` leaves anywhere (visible by inspection of
`status_overall_*` columns). SWE-agent has 7 BLOCKED leaves across
6 pilots (`f_02`, `f_03`, `f_05` ×2, `f_07`, `f_08`, `f_10`),
generated by the protocol's stuck-loop rule firing on real
pathological traces.

**Implication:** the BLOCKED status code is exercised only by real
traces. Tests / models that never see a BLOCKED row will drop the
discrimination.

### 3.4 Active denominator size

Roughly comparable (toy median 4.5, SWE-agent median 4.0). Toy
runs have larger maxes (one toy run peaks at 9 active leaves vs
SWE-agent max 7) because some toy runs were designed with deeper
splits. Splits are essentially absent in SWE-agent (0 splits across
20 pilots) because retrospective annotators rarely surface a
"vague subtask becomes several leaves" decomposition; the trace
shape doesn't usually demand it.

**Implication:** if a feature relies on `num_splits_so_far` being
non-zero, it will not fire on real traces. SPLIT_SUBTASK is real
and protocol-supported but does not surface much in retrospective
SWE-agent annotation.

### 3.5 Reopens are about equally rare on both, in opposite shapes

Toy/live: 6 reopens across 6 runs. SWE-agent: 3 reopens across 3
runs. Per-run, reopens stay rare (≤1 per run in both populations),
so models that depend on "many reopens" won't see them anywhere.
The reopen events that do exist are different in character: toy/live
reopens were authored to demonstrate the framework's non-monotonicity
support; SWE-agent reopens (`s_03`, `s_05`, `f_09`) are all **forced
by the trace** (a re-run repro showing the previous fix was insufficient,
or a final edit happening after the last validation). The latter is
the empirically grounded form.

### 3.6 Final-success label divergence

The dataset builder's `final_success` field for SWE-agent runs is
**`inferred_from_test_output`** (the upstream `eval_logs` content
written to `test_output.txt` by C3). For 3 of the 10 upstream
successes (`s_03`, `s_06`, `s_09`), the builder's heuristic
classifies them as failures despite the upstream `target` being
`True` and the eval log presumably containing pass markers. The
builder's heuristic was tuned on toy/live `pytest` output; SWE-agent's
SWE-bench-style eval logs may format pass/fail markers
differently.

**Authoritative upstream label** for any analysis that depends on
the truth of pass/fail is `source_metadata.json:final_success`
(present in every run dir, populated by C3 from upstream `target`).
The dataset builder's inferred label is a separate signal worth
keeping but not interchangeable.

This is a real follow-up: the builder's `resolve_final_success`
heuristic should be source-aware (via `source_metadata.json:source`,
which equals `"swe_agent"` for our runs) and short-circuit to
`source_metadata.json:final_success` when present. Tracked for a
future commit; **not** patched in F4 because changing classification
mid-stream would invalidate G's leave-one-run-out predictions before
they're computed.

## 4. Are SWE-agent traces "more diverse" than toy/live?

**Yes, in three concrete senses, and the diversity is exactly the
kind that makes the framework's claims empirically testable:**

1. **Distribution shape:** SWE-agent populates all four
   success/progress quadrants; toy/live populates two. The off-
   diagonal quadrants are where progress and outcome decouple.
2. **Failure-mode richness:** SWE-agent failures span 0.50–1.00 in
   coding-progress; toy/live failures bunch at 0.60. SWE-agent
   failures are produced by distinct mechanisms (stuck loops, no
   in-trace validation, hidden-work gaps, harness force-quit), each
   leaving a different ledger shape.
3. **Status-code coverage:** SWE-agent exercises BLOCKED (7 leaves)
   and INVESTIGATION drop-source (14 step rows); toy/live exercises
   neither.

## 5. Toy/live properties that do **not** survive on real traces

Three toy-corpus properties that a modeler trained on toy/live alone
would mistakenly believe were universal:

1. **Monotonic progress curves are common.** 4 of 18 toy runs are
   strictly monotonic. **0 of 20 SWE-agent runs are.** Any
   feature like `is_strictly_monotonic` will be near-constant
   (always False) on real traces.
2. **All failures end at progress < 1.0.** 3 of 3 toy/live
   failures end at coding-progress 0.60. SWE-agent has 1 failure
   at exactly 1.00 (`f_06`) — the framework's load-bearing
   counter-example.
3. **`SPLIT_SUBTASK` events occur regularly.** 8 splits in toy/live
   across 8 runs vs 0 splits across 20 SWE-agent runs.
   Retrospective annotation rarely needs the operation; live /
   forward-looking annotation in toy was where it surfaced.

## 6. Implications for downstream work

- **Modeling (Workstream Q):** train and evaluate on a mix that
  includes the off-diagonal quadrants, or the channel reduces to a
  thin `final_success` proxy. Toy/live alone is insufficient.
- **Predictive baseline check (Workstream G):** when the smoke
  script's `progress_only` baseline is run on the SWE-agent step
  table, expect it to do **worse** than on toy/live, because
  progress on real traces is a noisier proxy for outcome — exactly
  the desired property.
- **Visualization (Workstream L):** any dashboard that buckets
  runs as "low / mid / high progress" should show all four
  outcome × progress combinations using SWE-agent rows; toy/live
  rows alone will leave half the quadrants empty.
- **Future schema work:** the BLOCKED status code and
  INVESTIGATION drop-source have meaningful real-trace
  populations now. Anything that gates on having ≥1 example of
  each can use the SWE-agent rows.

## 7. Caveats

- N=20 SWE-agent traces is a pilot, not a full distribution. Some
  shape rates (3/20 reopens, 1/20 success-low-progress) have wide
  binomial intervals and should not be over-interpreted.
- All 20 SWE-agent annotations are by one annotator (me).
  Workstream H needs to confirm the shape distribution is
  reproducible before treating these rates as ground-truth.
- The `source_metadata.json:final_success` vs builder-inferred
  `final_success` divergence (§ 3.6) is real and worth fixing
  before G claims anything about prediction performance.
