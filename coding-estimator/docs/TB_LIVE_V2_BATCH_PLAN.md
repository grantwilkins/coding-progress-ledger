## 0. Pre-flight checks (one-time)

Before Batch 0:

```text
[ ] coding_estimator/runner/run_internal_task.py implemented per
    docs/TB_LIVE_V2_RUNNER_SPEC.md
[ ] coding_estimator/runner/transcript_to_events.py implemented and
    tested (tests/test_runner_transcript_to_events.py)
[ ] smoke run on tasks/tb_live_v2/low_progress_success_01_oneline_fix
    end-to-end: subagent → transcript → events.jsonl → ledger.jsonl →
    verifier → final_success captured
[ ] verify the 5 shipped internal tasks pass the verifier when their
    solution.sh runs verbatim (oracle smoke; no subagent)
```

We do **not** depend on the upstream `tb run` harness, Docker, or
direct Anthropic API access. The runner uses the Claude Code Agent
tool to spawn Sonnet/Opus subagents on a per-run basis; isolation is
a fresh tempdir + per-task fresh venv. See
`docs/TB_LIVE_V2_RUNNER_SPEC.md`.

## 1. Batch plan

Per TASKS.md U4. Each batch ends with a rebuild + profile pass before
the next begins.

| batch | runs | task mix | gate after batch |
|---|---:|---|---|
| Batch 0 (pilot) | 10 | 5 internal scaffolds + 5 TB2 tasks (1 per major category) | confirm sidecar protocol; confirm dynamics labels fire on internal tasks; check infrastructure-failure rate < 10% |
| Batch 1 | 30 | 15 TB2 + 5 original-TB-easy + 10 internal | check pass rate ∈ [0.30, 0.70]; if not, **resample tasks** per U2 § "What to do if the first batch is all successes" |
| Batch 2 | 30 | 15 TB2 + 15 internal | shape diversity: confirm ≥ 5 progress drops, ≥ 3 validation_new_work in the 60 runs collected so far |
| Batch 3 | 30 | 30 TB2 (fill missing categories/failure modes) | confirm category mix is within ±10 percentage points of policy; confirm ≥ 25 failures total |
| reserve | 20 | targeted resampling to hit shape goals | only if shape-goal floors not hit by end of Batch 3 |

Final target: 100+ runs (Batch 0 + 1 + 2 + 3 = 100; reserve as needed).

Each run is a single TB harness invocation. Per arm, each task is run
exactly once. No retries except the single re-run allowed for malformed
ledger output (per U2).

## 2. Per-batch loop

```text
for batch in [0, 1, 2, 3, reserve]:
    1. select tasks per batch plan + sampling policy
    2. for each task, for each arm in [A, B]:
         uv run python scripts/run_tb_live_v2_batch.py \
                --task <task_id> \
                --arm <A | B> \
                --seed <batch_seed>
       (spawns one subagent via the Agent tool; arm A = Opus 4.7 at
       budget_lines = 30, arm B = Sonnet 4.6 at budget_lines = 20)
       collects: events.jsonl, transcript.jsonl, ledger.jsonl,
                 verifier_output.txt, run_manifest.json, run_notes.md
    3. uv run python scripts/build_checkpoints.py --source tb_live_v2
    4. uv run python -c "
       from coding_estimator.labels.build import write_combined_labels
       from pathlib import Path
       write_combined_labels(Path('datasets'))
       "
    5. profile:
       - pass rate this batch
       - cumulative pass rate
       - shape distribution this batch (dynamics + shapes labels)
       - category mix
       - subagent-failure rate (runs that finished with no done record
         AND no verifier signal — drop, do not count toward 100)
    6. write reports/tb_live_v2_batch_<n>_profile.md (autogenerated)
    7. gate decision: continue / resample harder / resample easier /
       stop (if budget exhausted) — per U2 anti-tuning rules
```

Parallelism: subagents are independent. The driver may run up to N
subagents concurrently (recommend N=4 to start; raise after smoke
confirms no contention on the shared events.jsonl directory).

## 4. Stop conditions

Stop and freeze the corpus if **any** holds:

```text
- 100 runs completed and shape goals (U2) all met.
- After Batch 3 + reserve: shape goals are at floor (15 progress drops,
  10 validation_new_work, 10 stuck/blocked, 5 high-progress fail,
  5 low-progress success).
- Cost cap reached (see § 5).
- Infrastructure-failure rate exceeds 25% in any single batch (suggests
  the harness or sidecar bridge is broken; fix before continuing).
```

Do **not** stop early just because pass rate looks good. The
corpus needs failure variety, not just failure count.

## 5. Cost discipline

Subagent calls run on the user's Claude account. Approximate envelope:

```text
arm A (Opus 4.7, budget_lines = 30):  ≈ 30 actions × ~3k input + 1k output tokens
arm B (Sonnet 4.6, budget_lines = 20): ≈ 20 actions × ~3k input + 1k output tokens

infrastructure: none (host CPU; tempdir + venv per run; no Docker, no GPU)
```

Estimate before Batch 0 and document in
`reports/tb_live_v2_cost_estimate.md`. If the estimate is uncomfortable,
drop Arm B (per U2 fallback) — Arm A alone delivers the failure floor.

## 6. Risks specific to execution

- **Verifier flakiness.** For each scaffolded task, run its
  `solution.sh` on a fresh tempdir/venv and confirm `pytest tests/`
  passes deterministically before the task enters the candidate set.
  Exclude the task otherwise.
- **Subagent prompt drift.** The transcript-emission contract is the
  load-bearing assumption. Pin the prompt template in
  `coding_estimator/runner/prompts.py` and version it. If the prompt
  changes mid-collection, that is a protocol change and must be
  recorded.
- **Workspace leakage between runs.** Each run gets a fresh tempdir
  AND a fresh venv. Do not reuse workspaces across tasks. The driver
  asserts `not workspace.exists()` before mkdtemp.
- **Host-environment contamination.** Tasks like
  `stuck_blocked_01_missing_dep_loop` rely on a specific package being
  *absent*. The driver verifies absence in the fresh venv (not the
  host) before declaring the task ready.
- **Outcome-tuning temptation.** When pass rate drifts outside band,
  the temptation is to swap models. U2 forbids this. The enforcement
  hook is the protocol-changes log.
- **Subagent action accounting.** If the subagent forgets to append
  to `.transcript.jsonl`, the ledger is missing events and the
  estimator's features are wrong. The driver post-checks that
  `len(transcript_lines) >= 1` and aborts the run as
  `infrastructure_failure` otherwise. Re-run once with the same
  config; if it fails again, drop the task.
